# Удалённый агент: от готового Telegram до MCP

Эта инструкция дополняет [локальный быстрый старт](start-here.md). Локальный
MCP и авторизованный Telegram ещё не дают доступ облачному агенту. Для каждого
клиента нужны выбранные владельцем права и защищённый транспорт; аккаунт и
сессия остаются на сервере. Не копируйте session-файл и не публикуйте MCP на
открытом HTTP-порту.

Ниже — один пример: Linux с user systemd и **OpenAI Secure MCP Tunnel** для
поддерживаемого клиента ChatGPT/Dot. Возможности аккаунта, названия пунктов и
CLI могут отличаться; если нужного пункта нет, оставьте этот этап непроверенным.
Для других клиентов доступны [примеры Codex и Claude](linux-service.md#подключение-codex-и-claude)
с отдельным защищённым HTTPS-маршрутом. Копирование bearer-токена в случайный
URL или отключение защиты не заменяет совместимую авторизацию.

## 1. Убедиться, что один backend уже работает

Устанавливающий агент следует [Linux-инструкции](linux-service.md): проверяет
архитектуру и существующее подключение, при необходимости подготавливает
user-service и локальный вход владельца. По умолчанию remote-профиль не получает
все чаты и не может отправлять. Владелец отдельно выбирает область чтения,
контакты и дополнительные действия. Системные службы включают только после
согласования; создание пользователя, открытого порта или новой Telegram-сессии
ради каждого клиента не требуется.

Для первой проверки можно разрешить один выбранный чат. Устанавливающий агент
заменяет `CHAT_ID` числовым ID из разрешённого каталога. Пример ниже создаёт
отдельный профиль `assistant` и использует существующую приватную директорию
установки. Команда подготовки не исправляет небезопасные права существующей
папки молча: при ошибке сначала проверьте её.

```bash
cd "$HOME/services/agent-telegram-mcp"
export AGENT_TELEGRAM_HOME="$HOME/.local/share/agent-telegram-mcp"
.venv/bin/python -c 'from telegram_setup.private_state import secure_directory; from telegram_setup.config import private_dir; secure_directory(private_dir() / "agent-tokens")'
.venv/bin/python -m telegram_setup.agents add assistant --chat-id CHAT_ID \
  --token-file "$AGENT_TELEGRAM_HOME/agent-tokens/assistant.token"
```

Токен профиля сохраняется в новый файл, не печатается и не передаётся как
session-файл. Если профиль с таким именем уже есть, не создавайте дубликат
наугад. Если владелец выбрал все чаты, вместо `--chat-id CHAT_ID` отдельно
используют `--all-chats`; доступ к контактам и отправке это не добавляет.

## 2. Владелец выбирает туннель и вводит runtime key

Владелец создаёт или выбирает свой туннель в Platform и подтверждает, что он
привязан к нужной организации и среде ChatGPT. Случайный старый workspace не
подходит только потому, что он есть в списке. Если личная привязка недоступна,
не требуется покупать Business наугад: сначала выясните доступный защищённый
маршрут. Само создание объекта не означает, что соединение работает.

Работающему `tunnel-client` нужен отдельный runtime key с правами Tunnels Read
и Use. Его создание и ввод выполняет владелец. Ключ не вставляют в чат, URL,
параметры команды, репозиторий или скриншот. Если у владельца уже есть общий
приватный setup-мастер из согласованной поставки, используйте его; он **не
входит в этот репозиторий** и не нужен для локального Telegram. Его отсутствие
не нужно скрывать или заменять второй веб-формой.

Как самостоятельный запасной путь есть `scripts/save_tunnel_key.py`: он читает
один ключ из скрытого Terminal-ввода или stdin и создаёт новый файл
`runtime.token` с правами 600 в приватной директории 700 вне Git. Существующий
файл не перезаписывается, значение не выводится. Скрипт не проверяет права
ключа, не создаёт туннель и не обращается в сеть.

Например, когда владелец находится на Mac, а согласованный SSH-доступ ведёт на
его Linux, агент может подготовить **эту команду без значения ключа**. Владелец
вставляет ключ в скрытое системное окно; `SSH_ALIAS` заменяется уже проверенным
адресом владельца. На Linux должен существовать родительский каталог
`$HOME/.local/share`, а проект — лежать в пути из Linux-инструкции.

```bash
/usr/bin/osascript -e 'text returned of (display dialog "Вставьте runtime key" default answer "" with hidden answer buttons {"Отмена", "Сохранить"} default button "Сохранить" cancel button "Отмена")' \
  | ssh -T SSH_ALIAS 'python3 "$HOME/services/agent-telegram-mcp/scripts/save_tunnel_key.py" --directory "$HOME/.local/share/telegram-tunnel-private"'
```

Для локального ввода на Linux можно запустить этот же скрипт в своём Terminal:
он использует `getpass` и скрывает ввод. Если окно/TTY недоступны, остановитесь
и подготовьте другой согласованный приватный ввод, а не просите ключ в чат.
При `already_exists` не заменяйте файл автоматически: сначала разберитесь с
имеющейся настройкой. При сбое сохранения проверьте состояние файла и права,
не выводя его содержимое. Файловые права не защищают от процессов того же UID
или администратора.

## 3. Привязать существующий MCP к туннелю

Агент проверяет установленный `tunnel-client --help` и архитектуру выбранного
официального бинарника. В проверенной версии CLI поддерживаются `init`,
`doctor`, `run` и файловый key reference `file:/path`; их названия и флаги
нужно сверить с установленной версией. Команда stdio должна указывать на
`gateway_server.py --transport stdio --agent ИМЯ_ПРОФИЛЯ`, использовать тот же
`AGENT_TELEGRAM_HOME` и, для systemd backend, `AGENT_TELEGRAM_MANAGED_BACKEND=1`.
Не вставляйте ключ в команду: используйте `file:` для приватного файла.

Пример для уже подготовленного Linux backend и профиля агента `assistant`.
Агент подставляет подтверждённый ID своего туннеля в локальную переменную;
это не runtime key. Команда MCP собирается с безопасным quoting путей. Не
выполняйте пример, пока владелец не согласовал удалённый маршрут:

```bash
export AGENT_TELEGRAM_HOME="$HOME/.local/share/agent-telegram-mcp"
export TELEGRAM_MCP_ROOT="$HOME/services/agent-telegram-mcp"
export TELEGRAM_AGENT_PROFILE="assistant"
export TELEGRAM_TUNNEL_ID="ВСТАВЬТЕ_ID_СВОЕГО_ТУННЕЛЯ"
TELEGRAM_MCP_COMMAND="$(python3 -c 'import os,shlex; p=os.environ["TELEGRAM_MCP_ROOT"]; h=os.environ["AGENT_TELEGRAM_HOME"]; a=os.environ["TELEGRAM_AGENT_PROFILE"]; print(shlex.join(["/usr/bin/env", "AGENT_TELEGRAM_HOME="+h, "AGENT_TELEGRAM_MANAGED_BACKEND=1", p+"/.venv/bin/python", p+"/gateway_server.py", "--transport", "stdio", "--agent", a]))')"
tunnel-client init --sample sample_mcp_stdio_local --profile telegram-agent \
  --tunnel-id "$TELEGRAM_TUNNEL_ID" --mcp-command "$TELEGRAM_MCP_COMMAND" \
  --control-plane-api-key-ref "file:$HOME/.local/share/telegram-tunnel-private/runtime.token"
tunnel-client doctor --profile telegram-agent --explain
tunnel-client run --profile telegram-agent
```

Команда `run` здесь работает на переднем плане; используйте поддерживаемый
способ supervision установленной версии для длительной работы. Не добавляйте
`--force`: если профиль уже существует, сначала проверьте его. После запуска нужны
свежий успешный авторизованный polling и ответ MCP. PID и `/healthz` отдельно
не доказывают авторизацию. Автозапуск tunnel-client после reboot на новой машине
требует отдельной настройки и проверки; готовые unit-файлы проекта запускают
Telegram backend и reader, но не создают tunnel-client service.

## 4. Установить и проверить клиент

В нужной среде ChatGPT установите личный MCP-плагин с этим туннелем и
сохраните штатные подтверждения платформы. Затем **сам удалённый агент**
вызывает статус, показывает несколько разрешённых диалогов и читает одно
выбранное владельцем сообщение. Не включайте содержание переписки в отчёт.
Права на отправку, файлы, опросы и ботов настраиваются отдельно; доступность
tool в каталоге не доказывает выдачу права или получение файла клиентом.

Отчёт разделяет этапы: Telegram read, созданный туннель, authenticated polling,
установленный plugin и фактический read агента. Непройденное остаётся
`not_checked`, `blocked` или `failed`; один успешный этап не заменяет остальные.
Подробнее: [Dot по шагам](dot-client-guide.md), [границы проверки](verification.md).
