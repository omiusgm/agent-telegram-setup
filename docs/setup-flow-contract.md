# Контракт общего браузерного setup: Telegram-компонент

Статус: **контракт, сверенный с существующими исходниками**, а не новый UI. Telegram-часть реализована в `setup_web.py` / `telegram_setup/web_setup.py`. Общий runtime-key компонент — `codex-fleet-mcp/setup-wizard`: сверены его `README.md`, `AGENT-RU.md`, `wizard.py`, `app.js` и `index.html`. Здесь указан пакетный путь без личного home; компонент поставляется оператором отдельно и не скачивается этим репозиторием автоматически. Живая авторизация клиента и настоящие ключи в этой документационной задаче не проверялись.

## Один владелец каждого шага

| Компонент | Ответственность |
| --- | --- |
| Telegram-модуль этого репозитория | Явный выбор возможностей, при необходимости Telegram login, одна сессия, shared backend, read-only gateway, отдельные права агента и Saved Messages MVP |
| Общий setup-мастер | Приватная форма для сервисов `telegram`/`codex`, формат ключа, опциональный metadata GET, отдельный credential bundle и handoff с file reference; polling, запуск служб и Dot он не проверяет |
| Устанавливающий агент / оператор | Соответствие личной среде, размещение credential на хосте runtime, конфигурация, authenticated polling и следующий шаг; не выводит ключ и не меняет production только из-за сохранения формы |
| Platform и ChatGPT | Самостоятельный вход владельца и подтверждения доступа, создание/привязка туннеля, создание и установка личного plugin |
| Dot | Реальные ограниченные MCP-вызовы и, только по поручению, один тест отправки с readback |

Существующий Telegram UI не должен обрастать второй независимой формой OpenAI runtime key. Устанавливающий агент ведёт один пользовательский маршрут, повторно используя Telegram-шаг и общий credential-компонент. Этот компонент не устанавливает Telegram, не создаёт туннели, не запускает и не перезапускает службы. Непроверенная часть остаётся `not_checked`; ярлык и пути берутся из фактической согласованной поставки.

## Уже существующие точки интеграции

- `setup_web.py` запускает owner-local Telegram UI; [параметры](web-setup.md). Его `/api/status` и результат `verified` относятся к Telegram MCP, не к туннелю или Dot.
- `mcp_client.py status` выполняет реальный initialize/list_tools/read probe; credentials и сессия в клиент не загружаются. Для status используется та же установка и тот же `AGENT_TELEGRAM_HOME`.
- `gateway_server.py --transport stdio --agent dot` предоставляет шесть read tools. Для явного Saved Messages MVP добавляется `--enable-saved-text`; отдельное право профиля и backend `send-text` проверяются независимо. [Семантика MVP](saved-text-mvp.md).
- `AGENT_TELEGRAM_MANAGED_BACKEND=1` запрещает gateway запускать конкурирующий backend вместо user-service. Абсолютные пути устанавливающий агент берёт из конкретной установки; в публичном гайде их заменяют условными обозначениями.
- Одна серверная сессия сохраняется. Общий мастер не копирует `account.session`, не извлекает вход из браузера и не меняет другие MCP-конфигурации автоматически.

Общий компонент запускает агент из его каталога через `python3 wizard.py --open` (Python 3.9+, macOS/Linux, стандартная библиотека). Владелец открывает приватный одноразовый launcher и выбирает Telegram; bootstrap и cookie/CSRF остаются за реализацией мастера. Не воспроизводите их в переписке и не вызывайте write routes в обход его flow. Для публичного Telegram-пакета это ссылка на существующий компонент поставки, не команда искать файл `wizard.py` в корне этого репозитория.

## Фактический handoff общего мастера

Новая запись сервиса `telegram` создаёт `credentials/telegram/runtime.token` и `credentials/telegram/handoff.json` **в выбранном приватном state-dir, вне Git**. Ранее сохранённые значения не читаются и не перезаписываются автоматически. Разрешено прочитать новый handoff: в нём `schema_version`, `service`, `tunnel_id`, `runtime_api_key_ref`, `validation`, `transport_configured`, `dot_connected` и служебные сведения. Значения ключа и его отпечатка в handoff нет.

Семантика `validation`:

- `format_checked=true` — проверена форма одного credential; двойная вставка отвергается, а не обрезается автоматически.
- `tunnel_read_verified=true` — online mode выполнил фиксированный HTTPS metadata GET и сверил ID; это подтверждение Read выбранного туннеля. Offline save оставляет false.
- `tunnels_use_verified=false` и `least_privilege_verified=false` — форма не подтверждает Use и минимальность всех прав opaque key. Это проверяют отдельно на этапе прав/polling.
- `transport_configured=false`, `dot_connected=false` — исходное состояние после сохранения. Значение `credential_saved_only` не приравнивается к подключению.

Сохранение происходит на хосте мастера. Если браузер/мастер находятся на Mac, а runtime — на Linux, file reference Mac нельзя передать Linux как работающий путь. Оператор согласовывает доставку **нового runtime credential** или проверенный loopback SSH route к серверному мастеру; Telegram-сессию и старые login-файлы не копируют. В источнике общего компонента удалённый forward отмечен как отдельно не принятый: не обещайте его живую готовность по одному наличию кода.

## Логические входы общего мастера

Ниже данные адаптера. Реальные `/api/state`, `/api/save`, `/api/close` принадлежат общему компоненту и защищены его локальной сессией/CSRF; используйте его поддерживаемый flow, не секретные payloads через MCP/LLM. Доступный ярлык и расположение state-dir сообщает компонент-владелец.

| Поле | Откуда берётся | Работа оператора и публичный пример |
| --- | --- | --- |
| Установка и профиль агента | Подтверждённая конфигурация оператора | Только условные публичные пути/имена |
| Область чтения, выбранные действия | Явный выбор владельца | Да, без личных chat/contact IDs |
| `TUNNEL_ID`, `ORG_ID`, `WORKSPACE_ID` | Проверенные Platform/ChatGPT UI и приватная настройка | Оператор использует свои подтверждённые значения; в публичной версии только placeholders |
| Runtime key | Ввод владельца в приватной форме | Значение — нет; в командах только поддерживаемая file/env reference |
| API ID/Hash, телефон, OTP, 2FA Telegram | Только при необходимом новом входе владельца | Нет; ввод в существующем Telegram-шаге, не через чат |
| Результаты диагностики | Штатный CLI/MCP с редактированием вывода | Только обезличенные логические итоги, без auth headers и переписки |

Ключ вводится по loopback-странице либо отдельно проверенному согласованному маршруту к ней и сохраняется приватно. Успешный metadata GET или сохранение credential не означает успешный polling. Наличие Telegram-сессии не заменяет runtime key. OAuth upstream также не является браузерным входом control plane tunnel-client.

## Независимые отметки готовности

Каждая отметка имеет состояние `not_checked`, `passed`, `blocked` либо `failed`, краткое доказательство и время проверки. Это логические этапы, не названия конкретных полей версии tunnel-client:

1. `telegram_read_verified`: ожидаемый аккаунт и ограниченное чтение через MCP.
2. `tunnel_created`: нужный объект и соответствие личному окружению подтверждены.
3. `runtime_polling_authenticated`: успешный авторизованный poll текущего runtime и доступный upstream; один process/health/ready недостаточен.
4. `plugin_installed`: правильная личная интеграция создана и установлена, доступна Dot.
5. `dot_read_verified`: настоящий вызов MCP из Dot прочитал согласованный чат.
6. `dot_saved_text_verified`: опциональный owner-approved вызов Dot получил `delivered_verified` и readback.

В итоговом маршруте сохраняйте эти отметки раздельно. Текущий `wizard.py` сам завершает только `credential_saved_only`; полный набор этапов заполняет отчёт оператора. Он не ставит зелёный статус «Dot подключён» по факту создания туннеля, записи ключа, PID или ответа локального SDK. При `401/403` авторизация polling не подтверждена. Иллюстрации и навигация по блокерам перечислены в [dot-guide-steps.json](dot-guide-steps.json).

## Что не входит в этот контракт

Новый публичный endpoint, изменение прав/служб без согласованного действия, автоматическое создание ключей или платных ресурсов, публикация пакета, автономная переписка, аппаратная привязка и OS-изоляция. Их отсутствие не блокирует разрешённый разовый MVP, но не позволяет объявлять такую защиту реализованной.
