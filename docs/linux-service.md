# Linux: общий Telegram MCP для dot и других агентов

Обновлено 25.10.2026. Код шлюза реализован. В отдельной Linux-установке уже проверены живой вход, два SDK-клиента, ограниченное чтение, запрет записи, отзыв доступа и restart/checkpoint. Внешнее HTTPS/туннель и вызов из dot ещё проверяются отдельно. Рабочий macOS stdio-режим сохранён. Полные границы — в [проверках](verification.md).

## Устройство

Один `telegram_setup.shared --persistent` держит серверную Telegram-сессию. Reader gateway обращается к нему через существующий приватный Unix socket и выставляет шесть MCP tools. Агентам не передаются session, API ID/Hash, телефон или 2FA. Codex/Work не выступает LLM-посредником при каждом чтении.

| Tool | Поведение |
| --- | --- |
| `telegram_status` | Проверка соединения и области агента, без идентификаторов аккаунта |
| `list_chats` | Разрешённые диалоги, `next_cursor`; для полного каталога отдельный проход `archived=true` |
| `list_contacts` | Только разрешённые контакты, страницы и поиск по имени/username |
| `read_history_page` | История по `after_id`, `until_id`, `next_after_id` |
| `search_messages` | Поиск внутри одного разрешённого чата |
| `get_messages` | Обычная страница недавних сообщений; для обновлений предпочтительнее `read_history_page` |

Отправки, загрузки/скачивания файлов, пересылки, редактирования, удаления, отметки прочитанности, административных операций и произвольного вызова upstream tools в шлюзе нет. Старый локальный MCP сохраняет отдельно выбранные владельцем возможности.

## Установка исходников и зависимостей

Проверяйте архитектуру `uname -m` и доступность user systemd. Установщик использует Python 3.11 и frozen lock upstream; системный Python не меняется. Для Ubuntu с systemd 255 подготовлены user units. Директория ниже обязательна для готовых unit templates.

```bash
mkdir -p ~/services
git clone https://github.com/omiusgm/agent-telegram-setup.git ~/services/agent-telegram-mcp
cd ~/services/agent-telegram-mcp
export AGENT_TELEGRAM_HOME="$HOME/.local/share/agent-telegram-mcp"
python3 bootstrap.py --permissions read
.venv/bin/python stage_linux.py
```

`uv` и Git должны быть доступны; для уже установленного uv вне PATH передайте `--uv /absolute/path/to/uv`. Staging создаёт пустой реестр агентов и устанавливает **выключенные** units. Он не авторизует аккаунт, не копирует сессию и не включает сетевой доступ.

## Вход владельца

Сначала согласуйте новый вход и способ подключения. Предпочтителен отдельный вход на Linux: не запускайте две копии одного auth key. API ID/Hash, телефон, OTP и 2FA владелец вводит в [локальном мастере](web-setup.md) или Terminal; из браузера авторизация не извлекается. Для мастера общего reader используйте `--reader-only`.

```bash
cd ~/services/agent-telegram-mcp
export AGENT_TELEGRAM_HOME="$HOME/.local/share/agent-telegram-mcp"
.venv/bin/python -m telegram_setup.login
```

Через SSH используйте интерактивный терминал. QR сканируется в Telegram → Настройки → Устройства. Пароль 2FA не отправляется агенту. Исходное подключение Mac сохраняется до проверки Linux; его права и настройки этим пакетом не заменяются.

## Отдельный доступ агенту

Реестр `agents.json` находится в приватной директории. Пустой реестр никому ничего не разрешает. Каждая запись имеет свой токен, срок, действия и числовые chat/contact IDs. По умолчанию нет доступа ко всем чатам/контактам и нет телефонов. Для примера ниже замените `CHAT_ID` разрешённым числовым ID; каталог для файла токена должен существовать и быть приватным.

```bash
.venv/bin/python -m telegram_setup.agents add dot \
  --chat-id CHAT_ID --token-file /private/owner/path/dot.token
.venv/bin/python -m telegram_setup.agents show
```

Токен записывается в новый файл 600 и не печатается. В реестре хранится его проверочный SHA-256. Для доступа к контактам укажите `--contact-id CONTACT_ID`. Флаги `--all-chats`, `--all-contacts` и `--include-phones` применяются только после явного выбора владельца. Для каждого агента создавайте отдельную запись и срок; не раздавайте общий токен.

Отзыв без перезапуска backend:

```bash
.venv/bin/python -m telegram_setup.agents revoke dot
```

Отозванный токен не проходит следующий HTTP-запрос, включая ранее открытый MCP-клиент. Фиксированный stdio-профиль также проверяется перед каждой операцией. Уже возвращённые данные отзыв не удаляет; начатую сетевую операцию нельзя считать автоматически отменённой. Для новой выдачи используйте новую отдельную identity.

## Запуск служб

После авторизации и согласования активации:

```bash
systemctl --user enable --now agent-telegram-backend.service agent-telegram-reader.service
systemctl --user is-active agent-telegram-backend.service agent-telegram-reader.service
loginctl show-user "$USER" -p Linger
```

Для работы после выхода из системы нужен корректный user manager/lingering. Если `Linger=no`, согласуйте настройку с администратором; не обходите его подтверждение. Units имеют restart с увеличением задержки, одну блокировку аккаунта и `UMask=0077`. Reader в managed-режиме не запускает второго фонового держателя, пока systemd запускает первый.

`agent-telegram-reader` слушает **только 127.0.0.1:8791**, требует bearer token на каждом HTTP-запросе, ограничивает Host/Origin и размер тела. Он не является публичным HTTPS endpoint. Снаружи требуется отдельно согласованный HTTPS reverse proxy в доверенной сети либо защищённый MCP-туннель. Не привязывайте его к `0.0.0.0`, не включайте публичный forwarding без защиты и не передавайте токен в URL.

## Подключение Codex и Claude

После настройки защищённого HTTPS-маршрута используйте [Codex TOML](../examples/remote-reader-codex.toml) или [Claude JSON](../examples/remote-reader-claude.mcp.json). Замените `.invalid` адрес действительным HTTPS `/mcp`, задайте **разные** токены в локальных переменных клиента и включите сервер. Значения токенов в примеры не вставляйте.

## dot через поддерживаемый плагин

MCP не переносится между агентами автоматически: dot нужен установленный плагин с доступным транспортом. OpenAI Platform не обязателен для каждого MCP; это один из способов дать сетевой доступ без публичного inbound endpoint. Для удалённого custom MCP ChatGPT документирует Server URL или Tunnel и OAuth/No authentication. Наш произвольный bearer header из Codex/Claude-конфига не считается доказанной авторизацией dot. Альтернатива туннелю — отдельно подготовленный HTTPS endpoint с поддерживаемым OAuth; нельзя ради простоты отключать аутентификацию личного Telegram.

Предпочтительный путь — [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels), работающий на Linux и использующий фиксированный stdio-профиль этого reader:

```bash
.venv/bin/python gateway_server.py --transport stdio --agent dot
```

Эта команда задаётся в конфигурации `tunnel-client`, а не отправляется Codex при каждом запросе. Туннель должен запускаться с тем же `AGENT_TELEGRAM_HOME`; серверный профиль `dot` должен существовать и быть включён. Если backend управляется systemd, задайте `AGENT_TELEGRAM_MANAGED_BACKEND=1` также туннелю.

Используйте актуальный официальный [tunnel-client release](https://github.com/openai/tunnel-client/releases/latest), подходящий архитектуре, и проверяйте SHA-256. Туннелю нужны отдельные Platform permissions, runtime credential и связь с нужным ChatGPT workspace. Наличие подписки ChatGPT или подключённого MacBook само по себе их не доказывает. Секрет вводится владельцем локально и остаётся на сервере.

После `tunnel-client doctor` и работающего клиента добавьте личный custom MCP plugin в ChatGPT Plugins, Connection: Tunnel. Выберите нужный tunnel ID, настройте допустимую аутентификацию, установите плагин и выполните чтение тестового чата **из dot**. Пользовательское согласование доступа и подтверждения платформы сохраняются. Шаблон или успешный Inspector не считаются вызовом из dot.

## Проверки и пределы

- Unit tests и HTTP-проверки: два SDK-клиента, общее upstream-соединение, разные разрешённые чаты, запрет прямых write tools, неверного чата и Origin, отзыв в существующем клиенте, контакты без лишних полей и FloodWait cooldown.
- `read_dialog_page` ограничивает запрос метаданных; `read_history_page` ограничивает сообщения без медиа. Пустая отфильтрованная страница может иметь `next_cursor` — продолжайте её.
- После обработки страницы сохраняйте `next_after_id` у клиента отдельно для каждого чата. Новые сообщения читаются с этого ID; переписывание/удаление старых сообщений требует отдельной сверки.
- Макетные тесты не проверяют настоящий аккаунт, внешний TLS, dot, восстановление VPN или перезагрузку компьютера. Проверяйте их отдельно; service restart не равен reboot.
- Файлы сессии остаются под владельцем Linux. Токены ограничивают сетевых клиентов; процессы с shell/доступом к секретам того же UID могут обойти gateway. Полная OS-изоляция и отдельный UID здесь автоматически не создаются.
- Cooldown HTTP gateway общий для его клиентов; исходный общий backend также сохраняет собственные ограничения Telegram. Никогда не обходите FloodWait созданием нового клиента или повторным входом.

Живая приёмка: два клиента, включая dot, читают согласованный чат через один Linux backend; запрещённые действия отклоняются; один доступ отзывается без остановки второго; после restart сохраняется чтение с checkpoint. Сохраните обезличенные результаты, не ключи, переписку или логи авторизации.
