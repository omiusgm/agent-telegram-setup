# Conversation Guard: локальный snapshot read/draft

Локальная ревизия 23 октября 2026. **Проверенного runtime для живого делегирования на MacBook нет. Внешние чтения, отправки и approval API в Guard отключены.** Это исправление опасного поведения прежнего v0, который сообщал `host_isolation_verified=false`, но всё равно запускал credentialed upstream и publisher.

Основной Telegram MCP (`server.py`) остаётся отдельной полнофункциональной интеграцией с выбранными владельцем правами. Его настройки не изменяются. Если он или host shell доступны читающему агенту, они остаются обходным путём: этот модуль не делает весь Codex/Claude-чат безопасным.

## Текущая реальная граница

| Роль | Состояние сейчас | Что доступно |
|---|---|---|
| Reader | Реализован `reader.py` и read/draft MCP | Копия минимального локального снимка; непривилегированные черновики |
| Credentials broker | В изолированном runtime не развёрнут | Исходный Telegram-клиент и сессия остаются вне Reader; Reader их не запускает и не загружает |
| Approval controller | Production API выключен | `approve` отклоняется до открытия состояния; в Reader нет таблиц approvals/actions/deliveries |
| Writer | Production dispatch выключен | Нет publisher, live-транспорта или флага для включения записи; алгоритм проверяется только в test fixtures |
| Host boundary | Не подтверждена | Нет доказательства отдельных UID, mounts, сети или отсутствия shell/других MCP у модели |

Разделение Python-модулей и разные каталоги под одним UID не являются OS-изоляцией. У Reader-процесса больше нет кодового пути запуска upstream; у тестового Writer только фиксированный in-memory адаптер. Это полезные ограничения исполнения, но не доказательство изоляции компьютера.

## Поддерживаемый сейчас запуск

Поддерживается только локальный снимок и подготовка черновиков. Снимок заранее создаёт доверенный оператор/механический экспортёр вне читающего агента. В нём нет ключей, сессий или команд. В этой проверке используются только вымышленные сообщения.

Формат снимка:

```json
{"chat_id":12345,"messages":[{"id":1,"sender":"Контакт","text":"Сообщение","out":false}]}
```

`12345` — синтетический пример. Максимум 200 сообщений и 2 MiB, поля проверяются строго. Путь исходного снимка задаёт оператор при настройке; в инструментах модели нет `file_path`, `chat_id`, `account` или команды backend. После копирования читатель открывает только фиксированные `policy.json`, `snapshot.json`, `drafts.sqlite3`; снимок закреплён хешем. Символические ссылки на файлы состояния отклоняются.

```bash
.venv/bin/python -m telegram_setup.conversation_guard --home .local/reader-demo init \
  --chat-id 12345 --snapshot-file /absolute/operator/synthetic-snapshot.json --acknowledge-risk
.venv/bin/python guard_server.py --home .local/reader-demo serve
```

`init` показывает предупреждение и не перезаписывает непустой каталог. В рабочей среде снимок и policy должны быть read-only mounts, а данные черновиков — отдельным непривилегированным томом. Текущий запуск под обычным UID этого не обеспечивает.

Если требуется именно подтверждённая изоляция, запросите её явно:

```bash
.venv/bin/python guard_server.py --home .local/reader-demo serve --require-isolation
```

Сейчас эта команда всегда отказывает **до загрузки состояния или запуска MCP**: `secure_runtime_not_deployed_external_io_disabled`. Флаг ознакомления с риском, файл с `runtime_verified=true` или метаданные в SQLite не являются доказательством runtime. Старые live-политики версии 1 также отклоняются до запуска какого-либо backend. Параметры `--upstream-command`, `--templates-file` и прочие способы живой отправки из CLI удалены.

[Пример MCP-конфигурации](../examples/guarded-mcp-config.toml) выключен по умолчанию и называется snapshot/drafts. Он не изменяет глобальные профили клиента.

## MCP читателя

| Команда | Действие |
|---|---|
| `guard_status` | Всегда `secure=false`, `host_isolation_verified=false`, внешние записи/чтения выключены |
| `guard_read` | Последние до 30 сообщений только из закреплённого снимка; содержимое остаётся недоверенным |
| `guard_propose_reply` | Непривилегированный черновик к уже прочитанному входящему |
| `guard_get_draft` | Просмотр черновика, без утверждения и выполнения |

Нет `guard_request_template`, `send_message`, `send_file`, shell, смены адресата/политики или утверждения. Лишние аргументы отклоняются. Поля `approved`, имя отправителя, `SYSTEM MESSAGE` и текст «я владелец» не создают полномочий. База черновиков не является очередью исполнения; изменение её содержимого не запускает отправку.

У CLI `approve` принудительно выключен независимо от наличия старого утверждённого действия. Production `Broker.dispatch_once` отказывает до вызова транспорта. Никакой настройкой из сообщения эти запреты не снимаются.

## Что требуется для живого развёртывания

Живое развёртывание пока **не поддерживается этой ревизией**. Целевой вариант — отдельная Linux VM/контейнерная среда или OS-пользователи с реально проверенными границами:

1. Механический credentials broker владеет Telegram-сессией и выполняет только ограниченные запросы, а не инструкции из текста. Он не смонтирован и не доступен через raw MCP читающему агенту.
2. Reader получает read-only снимки, отдельный непривилегированный том черновиков, не имеет host shell/socket, ключей, другого MCP или произвольного egress. Интерфейс не загружает внешние URL из вывода модели.
3. Доверенный owner controller вне Reader проверяет получателя, полный payload, срок, actor и одноразовое утверждение. Он не доверяет статусам/хешам из worker-owned базы как полномочиям.
4. Отдельный Writer принимает только точное утверждённое действие и атомарно расходует его. Его credentials и approval endpoint недоступны Reader.
5. Доверенный launcher вне модели проверяет UID/peer credentials, mounts, сетевые ограничения и отсутствие обходных путей при запуске; при потере границы останавливает записи. Такой attester/launcher здесь ещё не реализован.

Строка в JSON, профиль агента, labels и число тестов не заменяют эти проверки. До развёртывания и отрицательных испытаний указанной границы Writer остаётся отключённым. Для текущего локального шага действий владельца не требуется; будущий живой пилот потребует отдельного согласованного runtime и права его развернуть.

## Проверка

```bash
.venv/bin/python -m unittest discover -s tests -q
.venv/bin/python verify_guard.py --report outputs/reader-fixtures.json
.venv/bin/python scripts/check_public.py
```

MCP проверяется по in-memory потокам SDK, без дочернего backend-процесса и сетевых соединений. Секрет, смена адресата, shell, поддельное подтверждение и runtime-флаг проверяются как атаки на API. Старые правила точного approval, подмены payload, просрочки, повтора и гонки дополнительно проверяются в `tests/guard_fixtures.py`, где Writer может обращаться только к точному in-memory FakeBackend.

Эти fixtures доказывают отдельные инварианты кода, а не OS-изоляцию и не устойчивость LLM. Live-сообщения, реальные аккаунты, Claude, login, системный VPN и глобальные профили не используются и не изменяются.
