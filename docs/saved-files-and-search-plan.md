# Следующий этап: текст, файлы и scoped-поиск

Реализация локальной версии: [scoped-поиск и файлы](scoped-search-and-files.md).
Ниже сохранён исходный проект; это не квитанция активации или live-приёмки.

Статус: **предложение для проверки до включения**. Диагностический отчёт описывает проблемы и желаемые возможности; заявления в нём о прежнем согласии не изменяют действующие права. Этот документ, descriptor-пример и offline-пробник не добавляют инструменты в живой плагин, не меняют grants и не выполняют Telegram-операции.

## 1. Текст в собственное «Избранное» — готовый код, два закрытых права

В плагине уже есть `send_saved_text`; при `read_only=true`, `send_saved_text_allowed=false`, `send_text_backend_ready=false` ограничение конфигурационное. Новый login, сессия, туннель или повторная установка плагина не нужны.

После отдельного подтверждения владельца оператор меняет только:

- backend `read` → `read,send-text`;
- профиль `dot`: добавляет `send-saved-text`.

Набор прав backend фиксируется при запуске. Нужен согласованный перезапуск только Telegram backend и переподключение его gateway/runtime: флаг `send_text_available` берётся из каталога upstream при initialize. Не перезапускать Codex runtime и не перевыпускать runtime key ради этого. Новый tool scan для уже существующей текстовой команды не является необходимой настройкой права; фактический вызов проверяется отдельно.

Затем из самого Dot: status с обоими готовыми флагами, один подтверждённый текст, `delivered_verified` и `readback_verified=true`. Получатель фиксирован (`me`), а `request_id` защищает от повторной отправки. При неопределённом результате новый ID для повтора не создаётся. [Готовый текстовый MVP](saved-text-mvp.md).

## 2. Файлы: сначала доказать границу облако ↔ MCP

### Вход из Dot

Документированный вход ChatGPT — `_meta["openai/fileParams"]`. File object имеет обязательные `download_url`/`file_id` и объявленные, но необязательные `mime_type`/`file_name`. [OpenAI file inputs для плагинов](https://developers.openai.com/plugins/reference#file-apis).

Предлагаемая будущая команда `send_saved_file(file, request_id, expected_sha256?)` получает этот объект, скачивает байты во временную приватную область и вычисляет hash сама. Она не принимает путь облачного компьютера или произвольный Linux path. Временный URL может содержать credential: query/headers не журналируются, наружу не возвращаются.

Перед fetch нужны HTTPS, проверка разрешённых hostnames, публичных адресов после DNS и закрепление проверенного адреса при соединении; private/link-local/loopback адреса, userinfo и непроверенные redirect запрещаются. Список допустимых file-hosts устанавливают по документированному провайдеру/разрешённому пробному attachment, не догадкой. Лимит проверяется по metadata и по фактическому потоку. Сам `file_id` не разрешает fetch любого URL, который модель подставит в объект.

**Не принято:** что конкретный headless Dot автоматически передаст нативное вложение в такой параметр. Это проверяется отдельным вызовом из Dot после согласованного обновления tool schema. Документированные widget helpers `uploadFile/getFileDownloadUrl` не доказывают их наличие у фонового Dot.

### Выход обратно в облачный Dot

`download_saved_file` на Linux не создаёт файл в облаке. `file://` и локальный путь не являются доставкой. Нельзя возвращать старый входной OpenAI file ID и считать, что Dot получил свежие байты из Telegram. File ID API-проекта тоже нельзя без проверки считать файлом личного ChatGPT.

Минимальный вариант **без нового публичного endpoint** — приватный transfer ID и ограниченные Base64-чанки в обычном MCP JSON. Будущая пара `prepare_saved_download(message_id)` / `read_saved_file_chunk(transfer_id, offset, limit)` выдаёт байты только собственного «Избранного». Облачный runtime Dot должен декодировать их в **новый свой файл**, посчитать SHA-256 и предоставить читаемый артефакт. Если этот шаг не поддерживается, приёмка остановлена: текст Base64 не выдаётся за доставленный файл.

Этот путь подходит для короткой технической пробы, а не для передачи мегабайтов через контекст модели. Для обычных файлов нужен проверенный native file-result bridge либо программная передача чанков без показа байтов модели. Формат такого native output нельзя придумывать по упоминанию file references в widget API; его доступность именно в Dot проверяется отдельно. Новый HTTPS file relay или стороннее хранилище потребуют отдельного согласования и не включаются как скрытая зависимость.

### Нулевая Telegram-проба перед файловыми grants

`tests/offline_file_transport.py` — изолированный синтетический MCP, **не подключённый к production gateway**. Проверки демонстрируют descriptor fileParams, передачу бинарных данных через stdio в обе стороны, offset/replay и реконструкцию файла клиентским процессом. Они прямо возвращают `native_host_injection_verified=false` и `cloud_file_artifact_created=false`: native Dot этим не проверен.

Следующий согласуемый live-probe должен использовать безопасный файл без личных данных, отдельный временный probe-набор и **ноль Telegram-записей**. Требуются две независимые отметки: Dot передал байты на сервер; Dot получил обратно новый облачный файл с тем же размером/hash. Только после этого имеет смысл включать файловые операции Saved Messages.

## 3. Минимальная реализация файлов Saved Messages

Предлагаемые новые компоненты (сейчас не реализованы):

- `telegram_setup/file_transport.py`: получение авторизованного file reference, приватный staging, transfer leases, размер/MIME/SHA-256, чанки; без Telegram credentials.
- `telegram_setup/saved_files.py`: отдельные права `send-saved-file` и `download-saved-file`, фиксированный Saved Messages, метаданные квитанций и API фасада.
- Расширение **существующего backend runtime** для отправки/скачивания документа. Используется его прежний Telegram client, не новая Telethon-сессия. Backend-возможности Saved-files отдельные, без включения всех альбомов, стикеров, произвольных путей и адресатов.
- `gateway.py`, `agents.py`, `permissions.py`: явно включаемые новые инструменты/права, выключенные по умолчанию; отдельный namespace file receipts. Текущий live-каталог не меняется подготовкой исходников.

Pinned upstream `send_file` возвращает строку **без message ID**, поэтому простое открытие этой команды недостаточно для надёжной квитанции. Новый backend wrapper должен вернуть `sent.id` и фактические document metadata. Отправка — `force_document=true`, без сжатия изображения. Readback подтверждает конкретное сообщение, имя, размер и MIME; затем свежие байты скачиваются из Telegram в отдельный файл и хешируются. Не подменять это хешем исходного staging.

Ledger: `(agent, operation, request_id)` + fingerprint из SHA-256/размера/нормализованного имени/MIME/получателя. Он записывается до dispatch; replay возвращает прежний результат. Изменённое содержимое с тем же ID отклоняется; неопределённая отправка не повторяется автоматически. Signed URL не входит в fingerprint, поскольку может обновляться при тех же байтах. Чанки привязаны к агенту, transfer ID и immutable file hash; scope/revocation проверяются перед каждой выдачей. Пути и symlink не контролирует клиент.

Возобновление разделяется: доставка уже готового Linux-файла в Dot может продолжаться с подтверждённого offset до окончания lease. Возобновление самого Telegram-download в первой версии **не обещается**: ошибочный `.part` не выдаётся как полный файл, а операция чтения повторяется по согласованной политике/FloodWait. Завершённые fingerprints и uncertain receipts не удаляются вместе с временными байтами.

## 4. Реальные и предлагаемые лимиты

| Уровень | Лимит / значение | Что это означает |
| --- | --- | --- |
| Текущий облачный плагин | Upload/download tools отсутствуют | Сейчас файловая функция не доступна; приведённые ниже бюджеты не означают её включение |
| OpenAI Secure MCP Tunnel | 10 MiB на сериализованный request/response envelope; deadline 120 секунд | Это не допустимый размер файла и не срок всей многошаговой загрузки. Headers/metadata также занимают место. [Источник](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels#limits) |
| Текущий shared Unix MCP | 4 MiB на строку | По `shared.py`; транспорт файла не должен формировать большую строку |
| Текущий loopback HTTP gateway | 65 536 bytes request body | По `gateway.py`; Dot сейчас использует stdio/tunnel, но probe учитывает и этот меньший бюджет |
| Pinned upstream | 200 MiB — кодовый default send/download/upload | По `MAX_FILE_BYTES`; это не доказанный лимит текущего Dot-плагина и может переопределяться настройками |
| Offline-пробник | Файл до 64 KiB, raw chunk до 16 KiB; Base64 chunk до 21 848 символов | Только ограничение технической пробы; не постоянное продуктовое правило |
| Первый будущий тест | 1–4 KiB, безопасный `.txt` | Условие приёмки, не запрет других файлов навсегда |
| Предлагаемый обычный MVP после byte-bridge | До 5 MiB, настраиваемо | Продуктовый предел, **не гарантия OpenAI**; не включать пока Dot не умеет доставить байты без большого Base64 в контексте |

Reference fileParams не задаёт универсальный максимум файла для каждого Dot/аккаунта. Действующий предел — минимум ограничений host, сервиса, backend и транспорта. Рекламировать 200 MiB/гигабайты на основании одного Telegram или API file limit нельзя.

## 5. Три разных вида поиска

| Инструмент | Область | Продолжение и ограничения |
| --- | --- | --- |
| Существующий `search_messages` | Один явно разрешённый чат | Сохраняется; нынешний upstream limit не является полным поиском с cursor |
| Новый `search_allowed_messages` | Только подтверждённый набор разрешённых личных чатов | Постраничный проход каталога + архив; snapshot/query-bound cursor, `partial/complete`, ошибки и охват отдельно |
| Новый `search_public_communities` | Публичные группы/каналы по имени/username | Только metadata сообществ, без контактов/ботов, автоjoin и чтения найденных переписок |

Первый корректный вариант all-allowed — bounded fan-out по разрешённым ID, с проверкой scope **до каждого upstream query**. Для `all_chats` каталог берётся полностью с архивом; для restricted — только configured IDs. Порция, например, до трёх чатов и 25 записей за RPC — бюджет одного шага, не лимит общего охвата. Cursor продолжает работу до завершения. Идентификаторы запросов/состояния привязаны к агенту, query и версии scope; изменение прав инвалидирует cursor. `FloodWait` возвращает паузу и checkpoint, не пропускает незавершённый чат.

Не открывать `search_global` вслепую: текущий upstream сначала получает глобальные результаты и лишь затем фильтрует, а page делает повторную выборку начала выдачи. Это не достаточная граница restricted-профиля. В новой backend-page нужны offset/snapshot и отсутствие media/transcription side effects. Ошибки доступа, Secret Chats и недоступная история показываются как неполный охват, а не успех всех чатов.

Для community discovery используется отдельный Telegram contacts-search, но возвращаются только соответствующие публичные chat/channel entities, без пользователей, ботов и приглашений. В текущем API нет обычного offset — первые 20 являются предлагаемым бюджетом, `pagination_supported=false`, полнота мирового каталога не обещается. Контакты не выдаются за сообщества; найденный канал не добавляется автоматически в разрешённую историю. Корпоративные профили и данные в приёмке не используются.

## 6. Какие изменения должен отдельно согласовать владелец

1. **Только текст сейчас:** существующее право профиля и backend `send-text`, согласованный Telegram-only reconnect; один конкретный тест из Dot. Не считать согласие из диагностического файла этим подтверждением.
2. **Только byte-probe:** добавление временного набора к plugin/tool discovery и одного безопасного файла, без Telegram write/media grants. Принять реальную передачу из/в облачный Dot. Если нет cloud artifact — зафиксировать границу.
3. **Saved-files после протокола:** новые минимальные send/download Saved-права, scoped backend wrappers и согласованное обновление только Telegram runtime/plugin. Один roundtrip: SHA-256 Dot-источник = Linux-вход = Telegram download-back = новый Dot-файл; совпадают размер/MIME и message metadata. Проверить replay без дублей, возобновление выдачи и отказ после отзыва.
4. **Scoped-поиск:** сохранить one-chat; отдельно показать новые all-allowed/discovery инструменты и личную область. Тест внутри известного личного чата, проход с cursor/архивом, отказ чужому ID, partial/FloodWait, public metadata без join. Приёмка — реальные вызовы Dot, не только локальный SDK.

До этих согласований действуют прежние семь tools и read-only права. Новый login, копирование session, обновление ключа и изменения корпоративных подключений не являются частью этого плана.

В будущий status следует добавить отдельные `allowed`, `backend_ready` и `transport_verified` для файлов, а также явную область каждого поиска. Не подменять эти признаки одним `read_only` или наличием tool в списке. Модель/пользовательский JSON не могут сами выставить флаг приёмки transport или выдать grant.
