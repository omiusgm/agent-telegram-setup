# Выбранные фотографии через общий MCP

Подготовленный opt-in срез: `read_photo(chat_id, message_id)` возвращает настоящее MCP `ImageContent`, а не строку `[photo]` или путь на сервере. Он использует существующий общий backend и его Telegram-клиент. Дополнительный вход, новый сервис, публичные ссылки и передача сессии клиентам не нужны.

## Права

Требуются одновременно три условия:

- В сохранённых разрешениях установки выбрана capability `read-photo`. Остальные выбранные права нужно сохранить. Изменение snapshot требует согласованного перезапуска backend.
- В stdio gateway оператора задан `--enable-read-photo`. По умолчанию инструменты отсутствуют; HTTP-фасад остаётся без изменений.
- Агенту выданы `read-photo` и конкретные пары `photo_sources`. Даже `all_chats=true` не разрешает скачивание остальных снимков. Сохраняется обычный ACL чатов.

После согласия владельца оператор выдаёт точечный доступ локальной командой; ниже только синтетические ID:

```sh
python -m telegram_setup.agents grant-read-photo AGENT --chat-id -10012345 --message-id 123
python -m telegram_setup.agents revoke-read-photo AGENT
```

Отзыв убирает только фото capability и её источники; не меняет токен, срок, остальные действия и другие профили. Реестр перечитывается на запросах и после ожиданий. Отзыв блокирует также уже скачанные ресурсы, но не может отозвать байты, ранее полученные клиентом.

## Что возвращается

Поддерживаются фотография сообщения и документ JPEG/PNG/WebP. Для альбома читается только указанное сообщение: соседние элементы требуют отдельных разрешений. Аватары, видео, стикеры, анимации и сообщения с защитой от пересылки не входят в этот срез.

`read_photo` отдаёт уменьшенный JPEG для зрения и метаданные исходника. Для Telegram-фото «оригинал» означает наибольший доступный Telegram-вариант, обычно уже сжатый самим Telegram. Для image-document сохраняются байты документа. SHA-256 исходника и preview разные; `original_sha_basis` означает хеш скачанных байтов и проверку их чтением из staging, а не независимый серверный хеш Telegram.

`get_photo_original(staging_id)` и зарегистрированный ресурс `telegram-photo://original/{staging_id}` возвращают исходные байты. До 64 KiB они встроены как binary MCP resource, выше — resource link с работающим `resources/read`. Это стандартный MCP-ресурс, а не обещание появления облачного файла в ChatGPT. Входные пути, URL, получатель, account и чужой agent ID не принимаются.

Пределы: исходник 5 MiB, 20 миллионов пикселей, сторона 12000; preview до 1280 по стороне и 512 KiB. MIME сверяется декодером. Staging использует существующий ограниченный `files/agent-staging`, права каталогов 0700/файлов 0600, непрозрачные ID, привязку к агенту/источнику, 15 минут TTL и существующую квоту до 8 активных файлов агента. Просроченные файлы очищаются при следующем добавлении; TTL немедленно запрещает чтение, но не обещает таймер физического удаления.

Неполное скачивание, изменение/удаление источника во время чтения, ошибка MIME или декодирования не публикуют файл. При истёкшем file reference допускается одно явное обновление того же сообщения с проверкой неизменности media ID, вида, размера и MIME. Telegram SDK может сам обновить reference внутри download; перед публикацией источник повторно проверяется. Собственных бесконечных retries нет.

Ожидания ограничены: до 20 секунд на чтение сообщения, 45 на скачивание, 90 на операцию backend. Существующий Telethon может сам ждать короткий FloodWait в этих пределах; глобальные настройки клиента не меняются. Выброшенный SDK FloodWait возвращается как `telegram_cooldown` с `retry_after_seconds`; gateway и photo backend блокируют повторные фото-запросы на этот срок. Это не новый общий планировщик лимитов всех инструментов аккаунта. Ошибки не включают Telegram exception text, file references, пути или секреты.

## Проверка реального клиента

Временный stdio-флаг `--enable-image-probe` добавляет `image_transport_probe()` с фиксированным синтетическим PNG через `ImageContent`. Он не читает Telegram и не требует фото-grant. Клиент должен описать видимые элементы, отсутствующие в текстовых метаданных. После проверки временный флаг убрать. Одного ответа SDK или названия картинки для приёмки Dot недостаточно.

Раздельно фиксируются:

| Состояние | Доказательство |
| --- | --- |
| `downloaded_to_linux` | Backend скачал выбранный источник в staging |
| `exposed_by_mcp` | MCP вернул ImageContent/работающий ресурс |
| `actual_dot_can_see_pixels_or_file` | Настоящий Dot увидел пиксели или получил проверенный файл |
| `verified_original_sha` | Исходные скачанные байты совпали с сохранёнными по SHA-256 |

Сервер всегда возвращает `actual_dot_can_see_pixels_or_file=false`: состояние клиента не выводится из успешного ответа сервера. Внешняя приёмка записывается отдельно, после вызова именно существующим Dot. Получение исходника как нативного облачного файла с проверенным SHA — дополнительная независимая проверка, не следствие `ImageContent` preview.

Проверки без сети: `test_photos.py` и настоящий SDK stdio `test_photos_stdio.py` с `offline_photos.py`. Они проверяют синтетические photo/image-document/альбом, reference refresh, FloodWait, таймаут, отсутствие доступа/приватность/удаление, размер/MIME/неполное чтение, отзыв/TTL/агентную привязку, хеши, настоящие ImageContent и binary resource. Тесты не являются живой приёмкой Telegram или Dot.

Официальная документация описывает [MCP tool results без UI](https://developers.openai.com/plugins/build/mcp-server). Специфическая обработка ImageContent и файлов существующим Dot требует отдельного реального вызова.
