# Handoff агенту: Telegram MCP → личный Dot

> Подключи мой личный Telegram к моему Dot по этому репозиторию. Начни с AGENTS.md, README.md и docs/dot-client-guide.md. Проверь актуальную запись Telegram в каталоге решений и версию кода. Сохрани уже работающие сессию и backend. Не проси ключи, код или 2FA в чат: подготовь один общий локальный мастер. Сначала покажи и сохрани мой выбор прав; уже данный выбор не спрашивай снова. Один оператор ведёт Platform, credential и туннель. Отдельно докажи Telegram read, правильную личную привязку туннеля, authenticated polling, установку плагина и настоящий вызов из Dot. Текст в «Избранное» отправляй только по моему явному тестовому поручению с подтверждением результата. Не выполняй отправки, перезапуски или изменения авторизации ради проверки документации.

## Короткая последовательность

1. Проверить существующее подключение через штатный MCP-клиент; не читать credential/session файлы для диагностики. Для Linux использовать один общий backend и приватный Unix socket. [Linux](linux-service.md).
2. Согласовать минимальные возможности и область. Для первого чтения достаточно одного разрешённого чата. Полный обзор чатов/контактов и телефоны — отдельный выбор; право записи не следует из права чтения. Сохранить выбор.
3. Подготовить один мастер по [контракту](setup-flow-contract.md). Существующая Telegram-часть — `setup_web.py`; runtime key принадлежит общему setup-компоненту. Не писать ещё одну форму токена в этом репозитории.
4. Проверить соответствие личного Platform и среды Dot. Повторно использовать подходящий существующий туннель. Создание и необходимые подтверждения — действие владельца. Идентификаторы остаются в приватной настройке, не в публичном гайде.
5. Подготовить ограниченный runtime credential с Tunnels Read + Use. Владелец выбирает `Telegram MCP`, свой tunnel ID и вводит один ключ в общем мастере. Читать только новый handoff с `runtime_api_key_ref`; online metadata GET доказывает Read, но не Use/polling. Сохранение происходит на хосте мастера: для Linux runtime file reference должен указывать на согласованный Linux-хост. Установить бинарник под архитектуру машины из официального источника; проверить целостность и актуальный CLI.
6. Настроить stdio к существующему gateway, сохранив `AGENT_TELEGRAM_HOME` и managed backend. Подтвердить не только process/health/ready, но и успешный authenticated polling текущего runtime, правильный туннель и MCP initialize. При `401/403` остановить продвижение.
7. Подготовить личный custom MCP plugin: Connection Tunnel, верный туннель, подходящий upstream auth, затем установить плагин. Для нашего stdio режима правило No authentication пояснено в [шаге 5](dot-client-guide.md#step-5); на публичный HTTP его не переносить.
8. Из самого Dot проверить `telegram_status`, небольшой каталог и одно выбранное сообщение. Сохранять результат этапа отдельно; вызов setup-агента не засчитывается как вызов Dot.
9. Только при отдельном тестовом поручении активировать [Saved Messages MVP](saved-text-mvp.md) и выполнить один `send_saved_text` из Dot. Требовать readback; не менять request ID после неопределённого исхода.

## Отчёт без секретов

Вернуть для каждого этапа `passed / blocked / not_checked`, дату, ревизию, обезличенное доказательство и следующий шаг. Не выдумывать поля CLI; сопоставить реальный вывод с логическими критериями. Не включать email, реальные organization/workspace/tunnel IDs, полные личные пути, runtime key, Telegram API Hash, QR или тексты переписки в публичный отчёт.

Отдельно отметить: создали ли только объект туннеля; был ли authenticated polling; установлен ли plugin; выполнен ли настоящий read Dot; выполнен ли разрешённый write с readback. Если этап не проверен, прямо назвать его. При новой авторизации, сетевом доступе, изменении прав и браузерных подтверждениях сохранить согласования владельца; настройка возможности не является поручением отправлять сообщения.
