# Linux: один Telegram backend для нескольких агентов

Дата проекта: 24.10.2026. Это исходный архитектурный план. На 25.10.2026 реализован reader gateway; текущие команды и границы проверки — в [инструкции Linux](linux-service.md). Живое подключение dot пока не подтверждено.
macOS по-прежнему использует прежний stdio → Unix socket → общий backend.
Примеры клиентов ниже — шаблоны для будущего защищённого endpoint, а не подтверждение подключения.

## Что уже можно переиспользовать

- `telegram_setup/shared.py`: один держатель Telegram-сессии, независимые MCP-соединения через приватный Unix socket.
- `telegram_setup/relay.py`: лёгкий stdio-клиент без собственной Telegram-сессии.
- `config.connection_lock()`: эксклюзивная блокировка; второй backend не должен открывать тот же файл сессии.
- `server.prepare()`: закреплённый upstream, проверка владельца, общий выбор возможностей.
- `read_history_page`: чтение по `after_id`, верхней границе `until_id` и продолжению `next_after_id`, без загрузки медиа и отправки read receipts.
- Upstream имеет общий chat allowlist, но текущая обёртка не предоставляет отдельную политику каждому клиенту. Просто пробросить нынешний socket в сеть недостаточно.

## Минимальная схема

```text
Codex ── HTTPS + токен Codex ───┐
Claude ─ HTTPS + токен Claude ──┤
                               ├─ policy gateway ─ Unix socket ─ один Telegram backend
dot ─ плагин ─ Secure MCP Tunnel┘                                    │
                                                         сессия только на Linux
```

Это программные процессы, не LLM-посредник. Codex/Work не должен пересказывать запросы другим агентам.

1. Сохранить текущие entrypoints macOS. Добавить отдельный режим постоянной Linux-службы: нынешний shared backend завершается через 10 секунд после отключения последнего клиента.
2. Добавить узкий gateway поверх существующего соединения. Он проверяет агента, разрешённый инструмент и область данных до обращения к backend. Не передавать наружу произвольные upstream tools.
3. Для Codex/Claude — MCP Streamable HTTP с HTTPS и независимыми отзываемыми bearer-токенами. Начать с HTTPS внутри согласованной частной сети. Для клиентов вне неё отдельно выбирать доступный защищённый маршрут; частный URL не станет общедоступным от наличия токена.
4. Для dot — личный поддерживаемый плагин через Secure MCP Tunnel с фиксированным серверным профилем `dot`. Его права не определяются аргументом MCP-запроса. Туннель не даёт право обходить gateway. Другому агенту или другу нужен отдельный профиль/credential; не раздавать один общий доступ.
5. Провести живую приёмку на одном выбранном владельцем тестовом чате. До неё Linux/dot не считать подключёнными.

## Права и защита данных

По умолчанию агент отключён, список чатов и контактов пуст. Отдельная политика содержит agent ID, состояние отзыва, срок действия, числовые chat/contact IDs, явные разрешения и лимиты.

- Первая версия открывает только список разрешённых чатов, разрешённых контактов, поиск в выбранном чате и чтение истории. Публикация, отправка файлов, пересылка, изменение, удаление и `mark_as_read` отсутствуют в списке и отвергаются при прямом вызове.
- `readOnlyHint` — метаданные, не контроль доступа. Проверять вызов сервером независимо от клиентских `enabled_tools` и просьб агента.
- Списки, поиск и счётчики также ограничиваются политикой: нельзя сначала отдать весь адресный справочник или общий поиск и затем фильтровать их силами LLM. Глобальный поиск аккаунта первой версией не открывать.
- Для контактов задавать отдельную область: разрешение читать группу не открывает всю адресную книгу. Телефоны по умолчанию не возвращать.
- Привязать MCP-сессию и курсор к аутентифицированному агенту; не принимать principal из tool arguments. Проверять отзыв и срок при каждом запросе, включая уже открытое соединение. Уже выданные сообщения отзыв не удаляет из контекста агента.
- Проверять Host/Origin, размер тела, время запроса и разрешённый путь. Неправильная/отсутствующая аутентификация — отказ до вызова Telegram. Токены не передавать в URL.
- Токены выдаёт оператор вне MCP; агент не может расширить свои права. В реестре хранить проверочные хеши; исходный токен выдавать через защищённый локальный файл/ввод, не через чат, CLI arguments или логи.
- В логах только agent ID, название операции, статус, длительность и обезличенный идентификатор запроса. Не писать текст сообщений, HTTP headers, токены, API Hash или сессию.

## История и новые сообщения

Использовать существующий `read_history_page`, ограничив числовой chat ID политикой gateway. При первом проходе зафиксировать верхний ID снимка и читать небольшими страницами. После обработки страницы сохранять checkpoint отдельно для каждого агента/чата. Новые сообщения получать начиная с последнего обработанного ID, без повторной выгрузки всей переписки.

Повтор страницы должен быть безопасен: дедупликация по `(chat_id, message_id)`, checkpoint фиксируется после обработки. Не приравнивать `after_id` к синхронизации правок и удалений старых сообщений: для них понадобится отдельный журнал событий/окно сверки. Cursor/notification транспорта MCP сам по себе не заменяет Telegram checkpoint.

## Linux и авторизация

- Сначала определить архитектуру и версии. Использовать тот же закреплённый upstream и frozen lock; установщик уже выбирает Python 3.11 через uv. Не менять системный Python и не подставлять ARM-бинарник на x86_64.
- Держать секреты и raw socket под отдельным владельцем ОС; ограниченные агенты не должны иметь shell/чтение домашнего каталога этого владельца. Иначе токены gateway не создают границы от обхода через файл сессии.
- Отдельная systemd-служба backend, gateway и при необходимости туннеля; `UMask=0077`, ограниченные writable paths, restart с задержкой и корректное завершение. Сначала подготовить неактивные units, затем включать после согласования.
- Сохранить `flock` и startup lock; не отключать их ради systemd. Для постоянно работающей службы добавить явный persistent-режим, сохранив прежний idle-режим macOS.
- При обрыве VPN/сети — ограниченные повторы с backoff и jitter. FloodWait учитывать одним координатором на весь аккаунт, сообщать `retry_after_seconds`; не делать независимые бесконечные повторы каждым агентом.
- Новый отдельный вход на Linux предпочтительнее копии живой Mac-сессии. Альтернатива — согласованный перенос с остановкой исходного держателя и единственным новым держателем. Две активные копии одного auth key не запускать.
- Открытие сети, подключение туннеля и новый вход выполняются только после отдельного согласования владельца. Пароль/OTP/API Hash вводит владелец локально; авторизация браузера не извлекается.

## Клиенты и dot

- [Шаблон Codex](../examples/remote-reader-codex.toml): HTTPS URL и имя переменной токена. Пример выключен.
- [Шаблон Claude Code](../examples/remote-reader-claude.mcp.json): HTTP transport и подстановка отдельной переменной окружения. Не использовать токен Codex повторно.
- dot: в ChatGPT Plugins создать личный custom MCP plugin, выбрать Connection: Tunnel и нужный туннель, настроить поддерживаемую аутентификацию и установить плагин. Только после этого проверять вызов из самого dot. Manifest или успешный Inspector не являются такой проверкой.
- Для туннеля нужны доступные в аккаунте Platform tunnel permissions, связь с нужным workspace и отдельный ограниченный runtime credential. Это ещё надо проверить в аккаунте. Credential туннеля остаётся на сервере и не заменяет агентский ACL.

## Приёмка

1. Два независимых клиента, включая dot, читают одно заранее выбранное сообщение разрешённого тестового чата. Серверные доказательства показывают одного держателя session lock.
2. Обращение к запрещённому чату/контакту и прямые попытки `send_message`, `send_file`, `edit_message`, `delete_message`, `mark_as_read` отвергаются до upstream. Живую отправку ради отрицательного теста не выполнять.
3. Отозвать credential одного клиента: новое обращение и обращение в существующей MCP-сессии запрещены; второй клиент продолжает читать.
4. Перезапустить backend/gateway/туннель: клиент восстанавливает соединение, checkpoint сохранён, повторной выгрузки нет. Проверить enabled/autostart units. Реальную перезагрузку всей машины согласовать и проверять отдельно, не выдавать service restart за reboot.
5. Проверить восстановление после временной потери маршрута для этих процессов, не меняя глобально работающий VPN. FloodWait проверить на синтетической ошибке, не провоцировать лимит реального аккаунта.
6. Выдать журнал проверок с датами и ограничениями, конфиги без секретов, команды выдачи/отзыва доступа и отката. Пока любого живого пункта нет, итог — частичная готовность.
