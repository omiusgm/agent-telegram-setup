# Управление своими Telegram-ботами

Экспериментальная часть. По умолчанию ни backend, ни удалённый агент не получают
эти действия. Тесты используют искусственных ботов и не создают учётные данные.

При отдельном разрешении можно включить чтение списка ботов, которыми владеет
текущий пользователь Telegram, и карточки выбранного бота. Источник — Telegram
`bots.getAdminedBots`; ни сообщения BotFather, ни токены не запрашиваются. Для
любого изменения имени, краткой информации или описания нужны отдельное право
агента и числовой ID конкретного бота. Перед операцией backend заново проверяет
владение и делает отдельное чтение после записи. Идентификатор `request_id`
должен быть постоянным для одной операции. При `uncertain_do_not_retry` не
повторять операцию с новым ID до проверки владельцем.

Установка использует существующий backend, сессию и выбранный stdio-профиль.
После согласования владельца оператор включает отдельно `agent-bot-read` или
`agent-bot-edit` в локальном выборе возможностей, затем только нужному агенту
может дать `grant-bot-read` и точечный `grant-bot-profile AGENT --bot-id ID`.
Клиентский флаг `--enable-owned-bots` включает интерфейс, но не выдаёт права.
Отключение записи для конкретного бота: `revoke-bot-profile AGENT --bot-id ID`.
На HTTP gateway этот эксперимент не включается. Изменения сервиса и плагина
требуют отдельной проверки выбранных прав и сохранения прежней конфигурации.

В этом экспериментальном коде подготовлен отдельный opt-in инструмент
`request_owned_bot`. Он использует существующий Telegram-клиент, обращается
только к проверенному `@BotFather` и отправляет фиксированные `/newbot`, name
и username. Он проверяет ожидаемые ответы, отправителя, идентификаторы и
попытки вмешательства с другого устройства; непонятный ответ останавливает
операцию. Включение требует отдельного backend-права `agent-bot-create`,
права агента `create-owned-bot` и флага `--enable-newbot` в его stdio-профиле.
По умолчанию всё выключено. Разрешение и установка на действующий сервер не
являются частью синтетического теста.

Для каждого создания нужны конкретные name, username и `request_id`. Доступны
два режима, которые владелец выбирает для конкретного профиля агента:

- **Оператор**, по умолчанию. После конкретного ответа владельца в клиенте
  оператор записывает одноразовую заявку через `python -m
  telegram_setup.newbot_approval --agent AGENT --name NAME --username USERNAME
  --request-id REQUEST --operator-observed-owner-confirmation`. Заявка отражает
  утверждение оператора и не удостоверяет личность человека криптографически.
- **Делегирование**, только при отдельном явном выборе владельца. После выдачи
  `create-owned-bot` оператор включает `grant-bot-delegated AGENT`; отмена —
  `revoke-bot-delegated AGENT`. Агент может создавать ботов по конкретным
  поручениям владельца без отдельной заявки оператора на каждое. Сервер знает
  профиль агента, но не умеет устанавливать, действительно ли конкретную
  команду дал владелец: это зависит от клиента и штатных подтверждений. Текст
  переписок и других источников может содержать инструкции, маскирующиеся под
  поручение; их нельзя считать разрешением. Нативные подтверждения не обходятся.

В обоих режимах процессы и SSH того же Unix UID могут обойти файловые права;
это не изолированный approval broker. MCP не принимает поле `approved=true` и
в квитанции указывает `owner_identity_verified=false`.

До первого сообщения сохраняется частная квитанция с резервным token_ref;
повтор с тем же `request_id` возвращает квитанцию без новой отправки, а
незавершённая попытка блокирует новое создание до разбора. После ответа
BotFather токен сохраняется только в локальном файловом хранилище, затем
проверяется владение ботом через Telegram. Агенту возвращается только opaque
reference, а не токен; этот reference сам по себе не является подтверждением
владения или правом читать файл. Хранилище `0700/0600` не шифрует файлы и не является
изоляцией от процессов или SSH того же UID. Ошибка после начала обмена —
`uncertain_do_not_retry`; не обходить её новой заявкой. CAPTCHA, 2FA, квота,
таймаут, непривычный язык ответа и конкурентная переписка также останавливают
операцию. Реальный named-create ещё не проверен: Telegram может менять фразы и
не всегда предоставляет строгую связь ответа с запросом. Telegram сохраняет
ответ BotFather в переписке, поэтому [граница фасада](botfather-output-guard.md)
не заменяет защиту файлов и процессов хоста.

Первый рассматриваемый сценарий — бот «Лев» для уведомлений владельцу. Для него
подготовлен инструмент `notify_owner_from_bot`: только точно разрешённый bot ID,
личный Telegram ID владельца получается из существующей пользовательской сессии,
произвольный получатель не принимается. По отдельному `agent-bot-notify`, праву
агента и точному bot ID выполняется один HTTPS `sendMessage`; отдельный постоянно
работающий бот-процесс не нужен. Токен берётся только внутри локального broker.
Доступны лишь боты с подтверждённой квитанцией создания и сохранённым токеном;
старые токены из переписки BotFather инструмент не извлекает.
Перед первым сообщением владелец должен начать диалог с ботом; это отдельный
согласованный шаг. `accepted_unconfirmed` означает, что Bot API принял запрос,
но чтение самим аккаунтом ещё не подтвердило сообщение. При неопределённости не
отправлять повторно с новым `request_id`. Отправка проверена исключительно на
искусственном транспорте и не включена в действующем подключении.
`getUpdates`, webhook, ротация/отзыв токена, перенос владения и удаление ботов
не входят в эту версию.
