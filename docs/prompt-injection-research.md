# Исследование защиты переписок от prompt injection

Проверено 23 октября 2026. Цель: сохранить удобное обычное подключение Telegram и отдельно ограничить сценарий, где владелец поручает агенту самостоятельно вести переписку.

## Вывод первого раунда

Сообщение собеседника может перенаправить модель к чужой цели. Проверка формулировок полезна для сигналов, но не должна выдавать разрешения. Нужны ограничения исполняющего компонента: кто может предложить действие, какой диалог доступен, что именно можно отправить и как подтверждение связывается с конкретным действием. [OWASP AI Agent Security](https://cheatsheetseries.owasp.org/cheatsheets/AI_Agent_Security_Cheat_Sheet.html) отдельно рассматривает проверку и атомарное расходование разрешений вне контекста модели.

Маркировка данных и разделение инструментов дополняют друг друга. MCP-аннотации описывают свойства инструмента, но не обеспечивают изоляцию или запрет утечек. Это прямо разграничено в [материале сопровождающих MCP](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/).

## Что проверено из готовых решений

| Решение | Что можно использовать | Решение для v0 |
|---|---|---|
| [Invariant Guardrails](https://github.com/invariantlabs-ai/invariant), Apache-2.0 | Правила над вызовами, ответами и контекстом выполнения | Подходит как более общий слой политик; для одного диалога оставлен узкий брокер на уже установленном MCP SDK |
| [Snyk Agent Scan](https://github.com/snyk/agent-scan) | Проверка компонентов агентной установки и MCP/skills | Проверка установки не заменяет разрешение каждого исходящего действия в переписке; не добавлен в путь сообщений |
| [LLM Guard](https://github.com/protectai/llm-guard), MIT | Входные/выходные сканеры, включая модель PromptInjection | Возможный дополнительный детектор; не источник полномочий. Зависимости включают Torch/Transformers, поэтому не добавлены в лёгкий v0 |
| [NeMo Guardrails](https://github.com/NVIDIA-NeMo/Guardrails), Apache-2.0 для библиотеки | Программируемые правила диалога и дополнительные проверки | Рассмотрен для более широкого агентного приложения; отдельный runtime сейчас не устанавливается |

Источники возможностей и зависимостей: [Invariant README](https://github.com/invariantlabs-ai/invariant/blob/main/README.md), [LLM Guard pyproject](https://github.com/protectai/llm-guard/blob/main/pyproject.toml), [сканер PromptInjection](https://github.com/protectai/llm-guard/blob/main/docs/input_scanners/prompt_injection.md), [NeMo README](https://github.com/NVIDIA-NeMo/Guardrails/blob/develop/README.md). Классификатор оценивает текст; это не проверка того, кому разрешено пользоваться Telegram от имени владельца.

## Что уточнил второй раунд

Старый адрес `invariantlabs-ai/mcp-scan` сейчас перенаправляет в `snyk/agent-scan`. Историческая документация `mcp-scan proxy` описывает runtime-правила, но её нельзя автоматически считать инструкцией к текущей CLI. Актуальный [Agent Scan README](https://github.com/snyk/agent-scan/blob/main/README.md) описывает сканирование установленных компонентов, API Snyk и необходимость согласования запуска обнаруженных серверов. Эти операции не выполнялись над личной конфигурацией или перепиской пользователя.

В модели угроз необходимо учитывать все инструменты агента, не один коннектор. Если агент может вызвать терминал, другой Telegram MCP или произвольный сетевой запрос, он может обойти защиту одного сервера. [Anthropic о границах sandbox](https://platform.claude.com/docs/en/managed-agents/secure-deployment-risks) различает поведение модели и реальные ограничения инструментов/среды. [OWASP MCP Security](https://cheatsheetseries.owasp.org/cheatsheets/MCP_Security_Cheat_Sheet.html) рассматривает фильтры и обнаружение инструкций только как дополнительные меры.

## Выбранная тестовая архитектура

Отдельный opt-in sidecar на имеющемся Python MCP SDK и стандартной SQLite. Это адаптация известных подходов — минимальных возможностей и внешнего контроля действий, а не новый детектор атак.

Один экземпляр обслуживает один личный диалог. Рабочий агент читает недоверенные сообщения, предлагает черновик либо выбирает точный шаблон владельца. Свободный текст утверждается по отдельному доверенному каналу. Политика, срок и содержимое входят в связывание действия; разрешение расходуется атомарно. После неизвестного исхода отправка не повторяется автоматически.

Главный критерий: даже если модель полностью подчинилась тексту атакующего, брокер не должен выполнить действие за пределами заранее выданных возможностей. Отдельная задача — обеспечить, что у рабочего агента вообще нет обходного пути. Это условие хоста, а не свойство JSON-обёртки.

## Проверенные результаты и ограничения

Первая версия: 50 unit tests, прежние 13 offline-профилей основного Telegram MCP и настоящий сквозной тест Guard → искусственный upstream → отдельная команда владельца. Отклонены 10 вариантов запрещённых инструментов/параметров. До утверждения свободного ответа записей нет; после него выполнен один точный ответ, отдельно проверен один статический автоответ. Проверены отзыв, бюджеты, неизменность действия, истечение срока, гонка двух исполнителей и неопределённая отправка.

Это проверка границ исполнения. Не проводились benchmark детектора на реальных атаках, испытание конкретной LLM, реальная автоматическая переписка или проверка sandbox клиента. Личные сообщения и ключи в тестах не использовались.

Независимый обзор Claude для этой экспериментальной ревизии ещё не приложен. Его нельзя называть совместным консенсусом до получения реального ответа и разбора замечаний.

Практическая инструкция: [Conversation Guard v0](conversation-guard.md).
