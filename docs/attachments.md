# Скачивание настоящих вложений через MCP

Opt-in набор `agent-attachments` + stdio-флаг `--enable-attachments` + agent action `read-attachments`. Используется существующая общая Telegram-сессия. Права действуют в уже разрешённой области чатов; отдельное ручное разрешение на каждое вложение не нужно. Ни отправка, ни изменение профиля, ни отметки прочитанности этим набором не включаются.

`download_attachment(chat_id,message_id)` получает реальный документ или прикреплённую фотографию выбранного сообщения. Возвращает metadata **и embedded binary MCP resource с байтами**, включая файлы больше 64 KiB. Для фотографий/поддерживаемых image documents добавляется `ImageContent` preview. Данные проверяются по размеру и SHA-256. Имя и MIME файла не являются инструкциями; содержимое файла недоверенное и автоматически не исполняется.

Инструмент не принимает локальный путь, URL, account, получателя или agent ID. Сохранение — только в существующий приватный файловый корень, с непрозрачным staging ID, привязкой к агенту/чату/сообщению, TTL 15 минут и действующей квотой staging. Максимальный исходник в этом срезе — 5 MiB. Защищённые сообщения не скачиваются. Неполный файл, несовпадение media identity после скачивания или ошибочный PDF header не выдаются как готовый результат. Ошибка file reference допускает одно обновление того же источника. FloodWait возвращается с cooldown; бесконечных повторов нет.

`get_attachment_original(staging_id)` возвращает те же байты без повторного скачивания Telegram. Зарегистрированный URI `telegram-attachment://original/{staging_id}` обслуживает настоящий `resources/read` с теми же ACL/TTL/hash checks.

Если клиент не умеет сохранять embedded binary resources, предусмотрен программный `read_attachment_chunk(staging_id,offset,limit)` — до 48 KiB исходных байтов за запрос, Base64 transport, стабильный полный SHA и next_offset. Клиентский код должен декодировать части в **новый файл на стороне агента**, проверить общий размер/хеш и только после этого считать файл полученным. Сам текст Base64, Linux path или metadata не являются доставленным клиентским файлом. Не следует выводить encoded bytes в ответ пользователю или вручную протаскивать мегабайты через текст модели.

Различаются Telegram download, MCP byte transfer, сохранённый файл клиента и native cloud artifact у конкретного агента. Сервер не может доказать последний шаг и возвращает `actual_agent_file_verified=false`. Настоящая приёмка требует клиентского readback размера/SHA. Этот транспорт не обещает создание нативного облачного файла произвольным MCP-host.

Для оператора: `telegram_setup.agents grant-attachments AGENT` и `revoke-attachments AGENT`. Отзыв немедленно закрывает инструменты и ресурсы на новых запросах, но не удаляет уже полученные клиентом байты. Изменение capability snapshot требует согласованного обновления backend; токен/сессия и остальные агенты сохраняются.

Проверки: `test_attachments.py`, `test_attachment_stdio.py`, общий `offline_peer_profiles.py`; используются синтетические PDF/image bytes и реальный MCP subprocess с отключённой сетью. Живая проверка отдельно сравнивает полученный Telegram PDF с исходным хешем, не публикуя его содержимое.
