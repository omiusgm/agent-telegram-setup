# Что проверено

## Reader gateway и Linux, 25.10.2026

- Код устанавливается на Linux x86_64 с Python 3.11.16 через frozen upstream lock; MCP SDK 1.30.0, Telethon 1.45.0. Системный Python 3.12 остаётся без изменений.
- На macOS и Linux x86_64 выполнены 107 unit/integration tests, включая прежние проверки. Reader gateway проверен настоящими SDK initialize/list_tools/tools/call через loopback HTTP и stdio на искусственных сообщениях.
- HTTP-клиенты имеют разные токены/чаты, но одно upstream-соединение. Проверены отказ чужому чату, прямые вызовы отправки/файлов/изменения/удаления/read receipts, отзыв уже работающего клиента, сохранение работы второго, отсутствие аутентификации и недопустимый Origin.
- Проверены cursor диалогов, фильтрация контактов до ответа агенту, отсутствие телефонных полей без выбора, incremental ID без дублей, cooldown после искусственного FloodWait и чтение после перезапуска протокольного сервера с checkpoint.
- Stdio-профиль для туннеля проверен через настоящий MCP, без Интернета и Telegram-auth: identity задаётся владельцем, подмена agent аргументом и отозванный профиль отклоняются.
- 13 offline MCP-профилей: базовый read-only — 62 tools, download — 64, reader — 68, assistant — 76, all-selected — 100. Новая read-only команда — `read_dialog_page`; макетные проверки не выполняют записи в аккаунт.
- Это не проверка нового входа Telegram, внешнего HTTPS, Platform tunnel permissions, plugin discovery, вызова из dot, реального VPN-обрыва или перезагрузки машины. Такие пункты фиксируются только после отдельной живой приёмки. Остановка/старт тестового HTTP-сервера не выдаются за reboot.

Команды и текущие ограничения: [Linux-сервис](linux-service.md). Результаты предыдущей ревизии ниже сохранены как история.

Дата: 23.10.2026. Платформа: macOS 27.0, Apple Silicon. Это результат конкретной проверки, не обещание работы любой сети или любой будущей версии.

## Рабочая техническая основа

Ранее в изолированной личной установке прошли вход по QR, ветка 2FA, сохранение авторизованной SQLite-сессии и read-only MCP-проверка чтения диалогов. Позднее после временных сетевых сбоев штатный сервер снова прошёл проверку соединения с существующей сессией. Личные ключи, аккаунт, переписка и результаты частных задач в этот репозиторий не переносились.

Публичный пример использует те же Telethon, pinned upstream и подход к конфигурации/блокировке. Интерфейс упрощён до Terminal; браузерный ввод пароля здесь не реализован. Запуск не прогревает всю историю диалогов автоматически: чтение происходит по запросу MCP.

## Проверки публичного пакета

- Чистое скачивание upstream по закреплённому commit и установка отдельной `.venv` через frozen lockfile: Python 3.11.16, Telethon 1.45.0, MCP SDK 1.30.0.
- 81 unit tests: приватное хранение, identity, блокировка и QR; явный выбор и сохранение прав; совместимость старых профилей и запрет подмены способа расшифровки; граница snapshot/draft Guard и отдельная модель утверждений на искусственном транспорте; общая служба, история и продолжение/отмена инвентаризации.
- 13 настоящих offline MCP initialize/list_tools: базовое чтение — 61 tools; чтение со скачиванием — 63; набор `reader` — 67; `assistant` — 75; все перечисленные возможности — 99. Каждая дополнительная группа проверена отдельно. Числа относятся к закреплённой версии; администрирование аккаунта и групп не включается.
- Прямой вызов не выбранного `download_media` отклоняется сервером. Подмена выбранного Telegram-распознавания на Groq отклоняется до обращения к провайдеру. Отправок и сетевых обращений к аккаунтам в этих проверках нет.
- Offline-сервер использует только синтетический API ID, нулевой тестовый Hash и временный каталог. Интернет-соединения блокируются; настоящий вход/отправка в этих тестах отсутствуют.
- Проверка публичного списка файлов и локальных Markdown-ссылок: `python scripts/check_public.py`.

Live-команда новой установки клиента проверяет чтение отдельно после его собственного входа. Не копируйте рабочую сессию с другого компьютера ради «зелёного теста».

## Общая служба и чтение

Два настоящих stdio-клиента на синтетическом backend получают один PID, независимые MCP-сессии и socket с правами 600. Отключение или некорректный протокол одного клиента не прекращают вторую сессию. Незавершённая инвентаризация удерживает backend во время пауз; явная смена прав позволяет ему завершиться после отключения всех клиентов. Повторный вызов со старыми правами отклоняется до операции.

Проверены верхняя ID-граница истории, ограничение размера страницы, allowlist, отличие владельца от администратора, архив и продолжение после FloodWait. Эти тесты не выполняют реальные операции Telegram.

## Conversation Guard 0.2.0

`verify_guard.py` проверяет настоящий MCP initialize/list_tools/call_tool через in-memory потоки SDK, без дочернего backend и подключения к Telegram:

- Reader предоставляет ровно четыре команды: статус, чтение локального снимка, создание и просмотр черновика.
- Десять попыток вызвать отсутствующую команду, подменить получателя, утверждение или runtime-статус отклонены.
- Зафиксированы нулевые обращения к сети, загрузки credentials, открытия файлов авторизации и запуски дочерних процессов.
- Старый live-формат policy отклоняется; `approve`, production dispatch и `serve --require-isolation` отказывают. Внешние чтения и отправки Guard выключены.
- Отдельные memory-only fixtures проверяют точный payload, срок, отзыв, повтор, гонки и неопределённую доставку. Они не подключаются к реальному Telegram и не включают production Writer.

OS-изоляция не развёрнута и не проверена; полноценный режим живого делегирования не заявляется. Независимый обзор Claude не завершён. Подробности и воспроизводимые команды — в [описании Guard](conversation-guard.md).

## Опыт операций с папками и переносом заметок

В отдельной рабочей установке проверялись инвентаризация собственных объектов, перенос в темы, checkpoint после FloodWait, сверка содержимого и архив перед удалением. Обобщённый порядок и ограничения включены в [инструкцию по переносу](notes-migration.md).

Частные отчёты, ID, переписка и временные операторские команды переноса не входят в публичный пакет. Этот опыт не означает, что закреплённый upstream умеет выполнять все операции одной штатной MCP-командой.
